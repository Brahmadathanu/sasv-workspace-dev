## 3. LIMS precedent — inspected, not copied
Live lab.fn_save_spec_override_direct supports ADD/MODIFY/DISABLE, product/item scope, validates base-line presence, deactivates prior active override and inserts replacement. lab.fn_review_spec_change_request_decision supports APPLY/REJECT and PRODUCT/FAMILY scope, records reviewer and changed scope, row-locks pending request, releases associated lock, creates product override or clones/activates family specification. lab.fn_create_effective_spec_snapshot_for_analysis freezes resolved lines into analysis snapshot. lab.fn_create_new_spec_version_from_edits clones and updates version, retires older active profile and activates new one.
These are useful patterns for local exception, approval and frozen provenance, but do not establish a verified one-analysis-only deviation facility. Do not assume it exists. Risks to review: caller-supplied user ID (auth.uid binding not visible in reviewed bodies; wrappers/ACLs not yet audited), snapshot resolver invoked twice (consistent source revision needed), direct override replacement concurrency, same-day effective-date boundary, family remap impact. No assertion of exploitable weakness without complete call-path review. PWL must bind actor to authenticated identity, lock/version-check changes, use one resolved snapshot and preserve all history.
Existing Production Route Manager already has rpc_create_product_route_draft, rpc_upsert_product_route_override, rpc_delete_product_route_override, rpc_validate_product_route, rpc_approve_product_route, rpc_clone_route_family_route_draft and rpc_approve_route_family_route. Use these governed authorities, not another master.

## 4. Conceptual relational responsibilities
Finalize actual tables only after dependency and feature inventory. Prefer typed normalized tables and FK constraints, not a wide EAV/spreadsheet replacement or arbitrary JSON as sole evidence.
- Batch production book: one identity per canonical BMR/batch instance, references product/BMR, lifecycle state, immutable route binding as of approved batch-start policy; prevent ambiguous reused batch number.
- Execution plan revision: frozen effective route lineage (family/product, exact revision, resolved steps), planned step instances, ordering/dependencies/mandatory flags, explicit amendment history. Snapshot is historical execution context, not independently authored master route.
- Stage execution: stable stage and occurrence identities, started/completed timestamps, actor, state, resource/location links, repeat/parallel execution, actual observations/yield/UOM and applicable typed payloads. Avoid duplicate product/batch fields where FK sufficient.
- Evidence and corrections: immutable signed completion/amendment events, reason, actor, source fingerprint, prior event links; mutable current projection derived transactionally. Previous pages remain visible. No hard-delete executed evidence.
- Route deviation/request: source stage/plan revision, ADD/BYPASS/REMOVE/REPLACE/REORDER/MODIFY, reason, impact, approval, scope and effective date, provenance of eventual master revision.
- Inventory: reuse authoritative existing FG ledger, packaging events/SKU counts, transfer and stock closure semantics; change FK/source references to execution identities. No second stock ledger, no independent text SKU breakdown authority. Receipt and posting atomic; shared preview/commit calculation, one batch lock order, idempotent request receipts. Exact measured excess only with authorization/evidence.
- Legacy lineage: old DWL ID maps to canonical execution ID, original source evidence retained, historical missing/ambiguous route or receipt clearly classified NOT_VERIFIED. Preserve original raw fields in governed archive if needed for legal/audit retention; not a live operational table.

## 5. Route evolution and page-turning experience
Batch library: search product/BMR/batch, resume active story, hold/resume, inspect completed books. Each page renders only relevant actual fields by stage/activity; use current approved route and existing activity masters. Completion advances to next eligible stage, not mechanically next index; parallel/repeat work, optional steps, partial progress and exceptions supported. Narrow/desktop responsive ERP design, canonical HOME, compact stage overview and previous/next controls; correction available in-page only with rights.
Two explicit scopes for practical change:
A. THIS_BATCH: approved plan amendment affects only current book; add or replace unexecuted stage, bypass with reason, remove unexecuted planned stage (tombstone in revision, not deletion), repeat/reorder where valid. Never erase executed evidence or silently invalidate downstream records. Mandatory FG/quality/safety gates cannot be generically bypassed.
B. CURRENT_AND_FUTURE: same local amendment plus proposal into existing product route draft/validation/approval workflow. Reviewer may approve future revision, reject, or retain batch-only; future batches inherit effective approved revision. Existing open/completed books remain pinned unless separately amended. Optional family-wide promotion is distinct high-impact approval, not default. Costing resource/cycle/sequence implications and LIMS/BMR quality requirements reviewed before approval. Distinguish actual deviation from master improvement, show both outcomes. No retroactive silent route edits.
Permissions: operate stage, complete/sign, correct prior evidence, approve batch deviation, propose master change, approve master route, stock/excess, supervise/read. Reuse canonical permissions where suitable; separate duties by risk, do not invent broad admin rights. Auth actor authoritative; optimistic revision and locks, no duplicate posting on retries.
