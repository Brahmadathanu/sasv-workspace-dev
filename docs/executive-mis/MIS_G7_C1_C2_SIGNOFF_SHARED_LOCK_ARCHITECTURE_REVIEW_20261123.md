## Verified live compatibility and permission facts

The existing ledger `public.fg_bulk_stock_ledger` keys movements by `product_id,batch_number`, with nullable section/subsection/area/plant identifiers. `public.daily_work_log` requires section/subsection/area, while plant is nullable. Current `public.event_skus` includes a nonnegative integer pack count and a parent packaging event. Work-log and event SKU core RPCs and stock triggers are existing legitimate writers. Authentication-based broad ledger CRUD is still present. The app's canonical `public.require_permission(text,boolean)` takes an existing module target but **no new C1 stage signer / C2 excess authority has yet been established**. A `SECURITY DEFINER` label by itself does not establish the needed authorization.

**Critical location transition evidence**: in November 1–21 (IST) all **80 FG bulk receipts** carried section/subsection/area; all **103 packaging stock depletion movements**, **37 force-close** and **4 auto-zero** rows had NULL location path, whereas both internal transfer legs had full location. The live ledger has 6,868 rows and 1,283 exact product/batch identities with zero blank/padded batch codes in the inspected snapshot. This proves **a strict location-aware stock balance cannot use current historical packing/adjustment rows without a source-backed location attribution policy**. Avoid assigning legacy NULL-location rows automatically to the current work-log location or arbitrarily splitting batch stock. This is a rollout blocker in addition to the 29 unlinked SKU lines.

## Proposed lock scope and writer convergence

For the transition, serialize on one durable `(product_id,exact batch_number)` identity, not on a nullable location tuple. This conservatively prevents two writers at separate locations from racing on a common batch while historical writers remain batch-scoped. The review-only table `app_private.mis_fg_batch_write_gate` has a primary key `(product_id,batch_number)`; the privileged writer first upserts the gate row without overwriting existing data, then selects it `FOR UPDATE` **before** reading availability or posting movements. This is a design only; **no lock table is installed**. Cross-batch actions lock keys in ascending product ID and batch code order to avoid cycles. If a transfer affects two distinct products or batches, lock all source/destination keys in that same global order. A batch lock does not itself prove location-specific quantity.

**All stock mutation routes must share the lock**: DWL source receipt/correction, packaging event SKU delta, auto-zero, force-close, transfer in/out including UPDATE/DELETE, helper functions, historical C3 replay and measured C2 excess. Restrict direct authenticated ledger mutation only in one coordinated, tested migration, with existing application operations preserved through authorized wrappers. If any legacy writer bypasses the gate, the concurrency guarantee is false.

New entries must carry explicit location identity and measure balance using nullable-safe comparisons for section/subsection/area/plant. Existing NULL-path deductions must be accounted for in an **unknown-location reserve/reconciliation bucket** until original documentary evidence supports assigning them to a location. Do not double count unknown entries in each physical location. Explicitly define facility-transfer reconciliation and stock balance as-of timestamps before authorizing location enforcement.

## C1 signed FG bulk stage authority

The reviewed model `MIS_G7_C1_C2_LOCK_AND_SIGNOFF_SCHEMA_REVIEW_ONLY_20261123.sql` captures immutable signoff event identity: product/batch, route ID/version, stage code, original BMR/work-log evidence references, measured positive base quantity/UOM, physical location, signer identity, signing authority and signed time, source projection hash, idempotency token and optional later supersession/revocation reference. An APPROVED route master or `daily_work_log.status='Done'` **is not itself a signature**. A signer must be separately authorized in the canonical permission system and verify actual batch-specific evidence, including the FG bulk stage.

Do not silently accept signed status from client parameters or auto-sign a historical batch when a positive FG receipt exists. If existing external/manual signed documentation is suitable, design a governed evidence import with real signoff and audit, not a synthetic blanket backfill. A later revocation must supersede prior signoff by append-only correction; a mutable state update is not sufficient. This is a design contract, not a completed table or role implementation.

## C2 authorized measured excess and packing

A separate private excess receipt references the valid C1 signoff and records product/batch, physical location, measured positive base quantity, base UOM, evidence, reason, signer and authorizer identities, linked packaging request and idempotency. The client can enter measured quantity/evidence in the approved in-page modal, but **server independently verifies both measurement and authority**; no trusted 'authorized=true' client flag.

The privileged server writer locks batch, confirms valid current signed FG stage and sufficient location-specific base quantity, calculates required stock from exact pack SKU and approved conversions, and, only when authorized, inserts measured excess and packaging event+SKU depletion in **one transaction**. Roll back all three on failure, preserving the prior batch and no partial posted event. A positive excess ledger entry is **not** automatically completed manufacture, nor equivalent to existing `fn_fg_force_close` / `fn_fg_auto_zero`.

For historical C3, a separate privileged, idempotent replay takes the actual source identity and checksum, checks an explicit signed historical FG bulk receipt/correction, and posts **only missing** pack consumption once. It does not modify an existing SKU count to retrigger the legacy trigger, and it never invents bulk from the 15,399 heterogeneous SKU pack units recorded in the November exception cohort.
