## 3. Required coordinated server architecture (design, NOT executable writer)

**Authoritative posting API:** a narrow, SECURITY DEFINER server procedure that owns the complete packaging intent, with stable `search_path` and role checks, accepting source product/batch/section/area/plant identifiers and requested SKU counts/units, immutable idempotency key, and *optional* signed excess-bulk intent fields (quantity, base UOM, evidence reference, reason). Monetary amounts and authorization flags are never accepted as trusted client assertions. It must resolve current actor from auth context, verify packaging CRUD and a **separate governed excess-bulk permission**, verify effective approved route AND actual signed FG bulk stage per batch, verify SKU pack size and base conversion from source, and calculate required base quantity on the server.

**Atomic sequence:** validate inputs and current source fingerprint → lock one consistent product/batch/location stock identity shared by every FG stock writer (use row-level lock on a durable balance identity or stable transaction-scoped advisory lock) → lock relevant work log/packaging source if needed → derive current base balance at transaction-consistent isolation → if requested exceeds available, require authorized recorded measured excess and source proof → insert immutable signed excess receipt and corresponding packing event/line and depletion in **one transaction** → audit old/new stock/source identity, actor, evidence and idempotency → return result only after commit. Any rejection must roll back **both** the excess receipt and pack line, preserving unchanged source and no partial Done state. Historical replay must be a *separate*, audited controlled writer, not the regular client packaging API.

**Lock coverage:** ALL competing writers (DWL positive receipts, force-close, auto-zero, internal transfer, packaging, authorized excess, historical replay, direct table DML paths) must obey compatible identity/lock ordering or be restricted. A lock used only by the new RPC would not prevent races with legacy direct writes. Validate location-aware balances and movements; batch-only `SUM` should not permit packaging against stock in another location. Avoid deadlock by specifying canonical lock order.

**Excess identity:** source-backed append-only receipt with event UUID/idempotency, product/batch/location/base-UOM, measured positive quantity, recorded evidence, reason, actor auth UID, approval authority, timestamp and linked packaging SKU/event/request IDs. A signed excess receipt is distinct from fabricated manufactured FG bulk or a force-close reversal. A qualifying FG bulk stage is still mandatory before an excess can be added to pack. Excess must be governed and auditable, never automatically inferred from requested pack counts.

**Historical C3:** isolate the 20 product/batch gaps from the 29 lines; first verify original BMR/weighment, old route/stock and unit conversion as-of historical date, signed owner approval, duplicate/source lineage, followed by a bounded insert-only receipt/correction and an idempotent pack-depletion replay linked to original event_skus IDs. Replay must verify exact source fingerprint and abstain if source changed or an identical depletion already exists. Never mutate `event_skus.count` solely to re-trigger an insertion, never auto-create an FG receipt of arbitrary packaging quantity, and never silently rewrite previously finalized reports.
