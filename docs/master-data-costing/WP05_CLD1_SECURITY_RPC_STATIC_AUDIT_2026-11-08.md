## 5. Proposal — no-side-effect verification design (FOR EXPLICIT FUTURE OWNER APPROVAL; NOT EXECUTED; no writer is ever invoked)

Principles: no mutating RPC on production to "prove denial"; no new users, grants or permission-table edits; no unreviewed preview calls.

1. **Static-only tier (can be done in repo with owner approval, no production):** for every RPC in §1, a reviewed trace of wrapper → internal → all callees with a tabulated *no-DML / no-volatile-callee / no-`set_config`/`dblink`/`pg_notify`* conclusion from `pg_get_functiondef` text supplied by the owner (catalogue readback is SELECT only). Output decides a **per-function, per-signature** allowlist entry proposal (one name at a time, F1 first), each with a static regression asserting the three layers stay non-mutating.
2. **Catalogue tier (SELECT-only, owner-run):** `pg_proc` properties (`provolatile`, `prosecdef`, `proconfig`, owner), `has_function_privilege` for `anon`/`authenticated`, and ACL for the SEC-A1/A2 functions; compare MD5s with the recorded post-apply values (SEC-A1: `50712d2c…`, `326211fd…`, `32077cdd…`; SEC-A2: `9911a0c6…`, as recorded in the SEC docs). Proves *configuration*, not behaviour.
3. **Behavioural negative tier (needs a separately reviewed plan):** use **existing** ID-N/ID-X/ID-O only if the owner supplies them; exercise *read* surfaces only (views and `rpc_get_*` already allowlisted) and assert HTTP denial / empty set as designed. Server denial of **writers** (SEC-A1/A2) should be demonstrated *without execution* via tier 2 (the guard statement is first in the body and ACL excludes anon) plus, if the owner insists on behaviour, a rollback-only transaction in a **non-production** copy — outside this brief.
4. **Pass/fail vocabulary:** `STATIC_PASS`, `CATALOGUE_PASS`, `BEHAVIOURAL_NOT_TESTED` — never record behavioural PASS from tiers 1–2.

Expected residual risk even after 1–2: the view-gate breadth in §3 (any-one-module view reads all 35 views), and unknown callees in candidate preview internals.
