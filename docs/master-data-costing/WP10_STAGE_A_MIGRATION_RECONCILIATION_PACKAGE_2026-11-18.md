## 2. Behaviour: three states, judged on the four tables as one unit, all inside one transaction
| State | Condition | Result |
|---|---|---|
| **A — original baseline** | each of the four tables has exactly its one original identity-only `FOR ALL` policy (`<t>_authenticated_crud`) AND all dependency checks pass | drops those four policies and creates the reviewed 16 Stage A policies (SELECT identity-only; INSERT / UPDATE USING+CHECK / DELETE require `app_has_permission(key,'view') AND (key,'edit')`), then re-verifies the exact end state; any mismatch rolls back |
| **B — already hardened (production)** | each table has exactly the 4 approved policies (names, commands, roles, permissive, expressions) AND all dependency checks pass | **verified no-op** — no DDL, no grant change, no data change; policy OIDs untouched |
| **C — anything else** | mixed/partial/altered/foreign/extra policy, wrong module key, Edit-only or View-only predicate, RLS off or forced, any grant outside `{owner, postgres, service_role, authenticated}` or any `authenticated` privilege other than exactly SELECT/INSERT/UPDATE/DELETE (⇒ Stage B applied), PUBLIC/anon grant, missing or drifted helper, any of the 12 `rpc_wp10_*` missing / not SECURITY DEFINER / owner without RLS bypass / wrong `require_permission(<module>,true)` target / wrong EXECUTE, SECURITY INVOKER writer of the four tables | `RAISE EXCEPTION 'WP10 Stage A reconciliation REFUSED …'` listing every problem; **nothing changes** |

"Exact" is judged against reference policies generated by the *same server* from the *same templates* into an `ON COMMIT DROP` temp table, so it is independent of PostgreSQL version pretty-printing (production is 17.4; local tests ran 16). No persistent object is created, no privilege granted, no function/RPC/trigger changed, no business data read or written. The migration never contains `GRANT`/`REVOKE`; Stage B is detected and refused, never performed.

**Why not just `02_stage_a_apply.sql`:** `02` refuses on any non-original state and would abort (safely) on production; it is also not a registration mechanism. **Why not an empty/no-op migration:** fresh or older databases that still hold the original policies would stay insecure. **Limit:** the four tables and the 12 RPCs are not created anywhere in `supabase/migrations`, so the chain cannot be replayed from an empty database; on any database missing them this migration refuses (State C), which is intended.
