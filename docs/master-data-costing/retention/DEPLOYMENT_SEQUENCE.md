Execution authority remains with the orchestrator after owner approval of each numbered step. **This package executed nothing against production.** Every step is a separate approval; stop on any failed check; each step has a rollback. No step changes cron jobs.

## Operational cutover (R3 requirement): the precise blocked consumer
Blocked consumer: **active pricing authority** — `costing.v_price_revision_feed_approved` / price-revision master views and `v_costing_period_run_status.is_latest_approved_period`, which today resolve to approved **October run 143** (September 122 is the prior approved period). November has no approved run, so the pointer shows the latest *unapproved* success (labelled "DRAFT run N – not approved"; R3 neither promotes nor hides it).
Consequence in the package: R4/R5 will **not** purge 143 or 122 (`ACTIVE_PRICING_AUTHORITY`) until an approved run exists in an authoritative month; all November detail is protected while November is the current month; after month turnover an unapproved November is an explicit governance HOLD.
Proposed fix (owner actions, not performed here): (1) at November month-end finalise and approve one November run through the existing governed RPCs (`rpc_costing_preflight_run` → `rpc_costing_finalize_monthend_run`/`rpc_costing_approve_run`); preflight now also asserts `DETAILS_AVAILABLE`; (2) confirm the price-revision feed's `is_latest_approved_period` moved to November and that Oct/Sep rows are no longer needed by the sheets; (3) only then does R5 release 143/122 (and earlier approvals) for purge. Alternative if the owner will not approve November soon: leave 143/122 as retained pricing authority indefinitely (they are two runs, not a growth risk) and purge everything else.
