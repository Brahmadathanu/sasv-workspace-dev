# R3 — exact-run consumer protection: what is integrated, what is excluded, what is exposed (26 Nov 2026)

Basis: repository definitions (live definitions are pinned/checked at install time by R3B; PREFLIGHT_06 section A supplies the live md5s). Server and client tests: `tests/07`, `tests/13`, `scripts/costing-retention/*.test.mjs`.

## Server

### Reviewed and deliberately NOT guarded
- **Writers and in-progress stage calculations**: all `rpc_refresh_*`, `fn_apply_*`, `fn_assert_stage04_snapshot_write_context`, `fn_au9_g4_capture_provenance`, `proc_*` — a new/in-flight run must keep calculating; terminal-run protection is the existing guard triggers.
- **Run header / governance paths**: `rpc_designate_costing_run`, `rpc_rebaseline_run_fingerprint`, `rpc_accept_*` (refuse purged runs on their own validation), `fn_verify/compute_run_fingerprint`, `fn_run_fingerprint_table_hash` (a purged run legitimately reports drift; approval and verification refuse it).
- **SQL-language numeric helpers** called inside writers/previews (`fn_build_*_as_of`, `fn_preview_*` sql, `fn_simulate_*`, `fn_internal_source_*`, `fn_total_manufacturing_*`): cannot be patched in place and are reached only through guarded readers or writers.
- **eAushadhi** `p_run_id uuid` functions: unrelated runs.
- **DEFERRED, need live definition**: `rpc_get_route_family_onboarding_status` (repo shows the permission call only in the writer), `rpc_get_product_sku_readiness` (no permission anchor in the repo definition; delegates to SQL helpers). Listed in the manifest as `DEFERRED`; the installer ignores them.

### Direct view/API exposure (explicit assessment)
`authenticated` users with the module permission can still `SELECT` the exact-run **views** (cost sheet, traceability, drilldown snapshots) with `refresh_run_id = <purged run>`. The result is an **empty set, never another run's data** (PostgREST view reads cannot raise without rewriting the live views, which are permission-gated and md5-pinned; not changed here). Mitigation: the Costing Suite client now routes **every** explicit-run view/RPC read through `costing-run-guard.js`, so the UI shows an explicit unavailable error instead of an empty/valid-looking result; the pointer view and period status keep non-guarded consumers from selecting a purged run. Residual: a custom API client reading a purged run by id sees zero rows. Proposed follow-on (needs live view definitions): add `fn_assert_run_details_not_purged` predicate to the views via a security-barrier wrapper.

## Client
`public/shared/js/costing-run-guard.js` is injected at the shell's single `costingFrom` / `costingRpc` choke point, so cost sheet, printable, traceability, monthly allocation trace, material/driver/route/QC/MS explain, review worklist (by-run), draft evidence, control-centre drilldowns and every other explicit-run path are covered without per-screen edits. Behaviour (8 unit tests): purged/purging ⇒ `RUN_DETAILS_UNAVAILABLE` error with the server reason (never an empty result, no data query issued); unknown / errored / thrown / malformed / wrong-run availability ⇒ fail closed `RUN_AVAILABILITY_UNCONFIRMED`; rows for a different run ⇒ `RUN_RESPONSE_MISMATCH`; 15 s cache with in-flight de-duplication, re-probe after expiry/invalidate (stale-state race tested); only `rpc_(get|export|preview)_*` exact-run readers are gated; writers, approval and the probe are untouched; period-scoped reads (cost comparison, run status/metadata) are not exact-run selections and stay available. Existing generation/latest-only loaders in the shell remain the stale-response protection. Approval screen: availability pre-check before any preview, explicit UNVERIFIED notice, **Verify run details** action; server gate refuses approval until verified.
Cost comparison (`costing-cost-comparison-read.js`) and the run-status screen are period/metadata reads through the governed pointer/status views (not explicit run selection) and were left unwrapped on purpose.
