# R6 physical reclamation plan and R7 Scheme Comparison retirement audit

## R6 — what a purge does to storage (do not conflate)
1. **Allocated bytes** (`pg_total_relation_size`): heap + indexes + TOAST. Baseline 20/21 Nov: ~18 GB across costing+public; top relations in `STORAGE_S0_…md`.
2. **Dead/reusable bytes**: after `DELETE`, space inside the relation becomes reusable by that relation after VACUUM; allocated size does **not** fall, and Supabase's disk meter does not drop. Expect the first months to *stop growth*, not shrink.
3. **Physically reclaimed bytes**: only a rewrite returns space to the OS: `VACUUM FULL` / `pg_repack` / `CLUSTER` (ACCESS EXCLUSIVE or table-rewrite, needs ~1× the live table size free plus WAL), or truncation of trailing empty pages by plain VACUUM (rare).
**Plan**
- A. Purge steps are bounded (`step_batch_rows`, one table per transaction). Each batch generates WAL ≈ rows × row width (+ index changes): size from `PREFLIGHT_04` 4a/4e; keep `max_wal_size` headroom ≥ 2 batches and watch replication slots before enabling.
- B. After a month's purge completes, run plain `VACUUM (ANALYZE)` on the touched relations during a quiet window (non-blocking). Measure `n_dead_tup` and `pg_relation_size` before/after; report reusable vs reclaimed separately in the receipt.
- C. Physical reclamation of the four large relations (traceability 3.5 GB, regional/signed evidence ~3 GB each, monthly 1.3 GB) requires a **maintenance window authorised by the owner**: prefer `pg_repack` (online, needs extension + 2× space) over `VACUUM FULL` (ACCESS EXCLUSIVE; blocks every costing read/write during the rewrite; WAL ≈ table size). **No VACUUM FULL / repack is performed or scripted for execution by this package.**
- D. Indexes: ~48 nested FKs lack a leading index. A purge deletes parents child-first, but PostgreSQL still probes each unindexed child per deleted parent. R4 blocks purge until each relevant edge is indexed or carries a recorded `index_waiver_reason`. Add only the indexes `PREFLIGHT_04` 4b shows for large children, `CREATE INDEX CONCURRENTLY`, outside a transaction, one at a time, owner-approved.
- E. Headroom rule: never start physical reclamation with < (largest relation size + 20 %) free allowance; confirm Supabase plan disk quota first.
Verification receipt per run: ledger `removed_row_counts`, `verification_digest`, `purge_step_receipt`; per month: before/after `pg_total_relation_size`, `n_dead_tup`, VACUUM timing.
