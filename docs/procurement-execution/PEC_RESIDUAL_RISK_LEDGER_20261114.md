| **R-1** | **Corrected; open, non-blocking** | *Earlier text (superseded):* "vendor bulk writers vs resync line-lock inversion." That is **wrong**. `proc_apply_vendor_to_same_item_lines_pec_internal` and `proc_clear_vendor_assignment_for_same_item_lines_pec_internal` never lock or update `proc_indent_line`. They upsert `proc_indent_line_sourcing_decision` rows and then `UPDATE proc_indent_header` (updated_at / updated_by) for **many indent headers in query order**, without the header-first protocol. They act on published indents (approved / issued), while resync acts only on drafts, so the two cannot form a cycle. The real residual: two multi-header writers (vendor apply vs vendor clear/apply on overlapping indents, or any other multi-row header updater) can acquire header rows in different orders and deadlock; PostgreSQL then aborts one transaction cleanly (SQLSTATE `40P01`, no partial state). Independent of R10. | R1a (an approved-line correction waits for the vendor writer's header lock, then applies), R1c (indent lines stay writable while the vendor writer holds header rows), R1d (resync of a draft is not blocked), R1b (20 concurrent rounds: observation only, 0 aborts; absence is not proof) | Accept with a documented disposition, or commission an ordered-header-update fix separately (order the header update, or lock headers `ORDER BY indent_id` first). Not part of #412. |

Database-level locks still serialise them with an in-flight resync: a direct new-line INSERT waits behind the resync because the live FK `proc_indent_line.indent_id -> proc_indent_header` takes `FOR KEY SHARE` on the header row, which conflicts with the resync's `FOR UPDATE` (R3a); a direct UPDATE of an existing line waits for the resync's line locks (R3b). What remains is only the absence of the wrapper's permission and audit-of-intent steps for trusted server code. | R3a, R3b PASS; G6 PASS; R3c INFO | Accept as the privileged-caller boundary.
