# PEC disposable draft-fixture test proposal (R10 follow-through)

Date: 14 November 2026 | Issue #388 | Base: staging `13b2c89c25fa73910ff2bcb73dcd43853325f477` | **Proposal only.** Nothing here creates production fixtures, touches live records, roles or grants, deploys SQL, merges or publishes. The signed-in Editor / View-only / No-access results (report `PEC_ROLE_ACCEPTANCE_REPORT_20261114.md`) are not repeated. Installed-PWA offline/device and launched-Electron-with-real-sessions stay tracked separately (§9).

## 1. Recommendation
**Extend the existing PG17 harness** (`scripts/pec-r10/`, workflow "PEC R10 SAFE resync concurrency PG17"); do not build a second framework. It already provides everything the plan needs: a synthetic schema, a seed function that rebuilds all rows, the real R10 / Add Line / PR-writer function bodies loaded from the repo, a deterministic barrier (advisory lock 777 + `pg_stat_activity` wait events, no sleeps), a state fingerprint, `RESULT <id> PASS|FAIL` output, and negative controls that must fail. Add four layers on top, in this order: **F1** safety hardening and a real RBAC/ACL layer; **F2** the writer and collision matrix; **F3** client behaviour driven by the server's *actual* preview JSON; **F4** characterisation of residual risks R-1/R-2/R-3. An optional **F5** adds an HTTP layer (PostgREST) — owner decision.
Already covered today (no new work, keep as regression): S1–S9 (SAFE collision/normalisation/adopt/RESET/denials), T1–T7 (manual edit, PR flip, PR edit, approval, same-indent, unrelated, deadlock), P1–P5 (preview content, READ ONLY, agrees with writer in 5 states, ineligible, ACL), SR1–SR8 (reassignment locks, ACL, permission-first). The fixture's Add Line wrapper body is byte-identical to the live installed function (md5 `7d295ab338d9337134585314920eab07`, equal to migration `20261112220000` and to the live read of 14 Nov).
Gaps found: (a) permission is a no-op stub, so genuine role gating and real grants are not exercised in the database fixture; (b) Add Line has only a negative test (S9) — no positive draft writes, no approved/issued/closed cases; (c) the preview's RESET counts are not compared with what RESET really deletes; (d) the approval test T4 uses a plain `UPDATE` of the header, **not** the real approval function, so R-2 is untested; (e) client tests use hand-written preview JSON, not server output; (f) no vendor-writer model for R-1.

## 2. Isolation (no production data, no credentials)
- A throw-away `postgres:17` instance: the GitHub Actions service container (as today) or a local container/cluster in a temp directory. This Windows machine has **no Postgres or Docker** (WSL Ubuntu has none installed): runs happen in CI, or after the owner approves installing PostgreSQL 17 in WSL for local reruns.
- Credentials: only the fixture-only password of the ephemeral service (`fixture_only`), no Supabase keys, no network path to the production project. Synthetic ids only (items 11–99, PRs 100–500, UUID users generated by the fixture).
- Hardening to add (F1), because the harness runs `dropdb --if-exists` by name on whatever `PGHOST` points at: (H1) refuse unless `PGHOST` is `127.0.0.1`, `localhost` or a unix socket; (H2) refuse if `PEC_FIXTURE_ONLY=1` is not set; (H3) database name = `pec_r10_<source>_<run-id>`, created by the run, never reused; (H4) refuse if the connected server has a `supabase_migrations` schema or any pre-existing `proc_indent_header`; (H5) `trap … EXIT` that terminates the `ctl` / `sess_*` backends and drops the database even on failure or Ctrl-C.
- Only **function definitions** (no data) may be copied from live for R-1/R-2 models (§6); they come from a read-only catalog read by a DB reviewer and are committed as sanitised SQL. Row data is never exported.

## 5. Repeatability, cleanup, rollback
- Each run builds its own database, reseeds with `fx_seed()` (TRUNCATE … RESTART IDENTITY) before every test, and drops the database in an `EXIT` trap. Every barrier backend is named (`ctl`, `sess_A`, `sess_B`) and terminated at teardown; every wait is bounded, so a stuck test fails instead of hanging.
- CI runs the guarded source twice in the same job and requires identical `RESULT` lines; a PR needs three consecutive green runs before the matrix is called stable. Negative controls extended: the legacy source must fail the new A/C items it should, and a deliberately weakened wrapper (no permission check, or granted to `anon`) must fail G1–G6.
- Teardown assertion at the end: no `pec_r10_*` database remains, no `ctl`/`sess_*` backend remains, no advisory lock 777 held.
- **Rollback:** nothing to roll back in production — the fixture is a separate disposable database and the proposal adds no migration. Any fix suggested by R1b/R2b is a separate migration that needs its own owner approval.

## 6. Residual risks — which can be exercised safely
| Risk | Safe in a disposable DB? | How / prerequisite | Outcome type |
|---|---|---|---|
| **R-1** vendor bulk writers vs resync (lock inversion → possible `40P01`) | **Yes**, with a faithful model | needs the live bodies of the vendor bulk writers and the vendor columns on indent lines (read-only catalog read by a DB reviewer); two sessions with a barrier and rows made physically out-of-id-order | characterisation (deadlock abort is fail-safe); fix is optional and separate |
| **R-2** approval vs resync stale line count | **Yes** | needs the live approval function body (structure seen on 14 Nov: reads status, counts lines, then updates, no lock first); barrier between count and update; PR final quantities driven to zero | reproduces a real, narrow defect; fix test only against a proposed migration |
| **R-3** privileged internal callers | **Partly** | access-control part (G6/G7) is enforceable and testable; the service-role bypass is by design and can only be characterised | PASS for the ACL part; documented boundary for the rest |
