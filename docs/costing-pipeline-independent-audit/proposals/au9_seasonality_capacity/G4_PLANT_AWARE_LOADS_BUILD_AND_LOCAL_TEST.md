## What G4 does
For each route step, G4 works out the loads per batch, i.e. how many machine charges the batch needs:
- Loads = ceil(batch charge ÷ capacity), and never less than 1.
- It never uses hours or time. The package fails if any G4 function references a time field.

**Order of resolution**

| # | Source | Used when | Result in run 9001 |
|---|---|---|---|
| 1 | **Machine named on the route step or product override** | The machine has a usable charge capacity on the date | Grinder 26 → 20 kg (6 steps per pool); wet grinder 174 → 2 kg (1) |
| 1T | Named machine is a throughput machine (kg/h) | **T1**: use the class weight lot; the rated kg/h is not a costing basis | Disintegrator (290 steps), capsule and tablet machines (44) → class lot |
| 2 | **Approved step rule** (governed activity; P26) | No usable named machine | Rasoushadhi "Grinding" → 20 kg (62); Kajjali → 3.2 kg khalvam (13); Pill grinding → 3 kg (29); pulverising, sieving and wet pulverisation → T1 class lot (620) |
| 3 | **Approved class fallback** (`capacity_fallback_policy`, approved in G1–G3) | Nothing else applies, or the named machine is pending, non-limiting, of another class or not operational (each gets a review flag) | All other steps keep today's class defaults |

**When it stops with an error instead of guessing (fail-closed)**
- The route names a machine that has no capacity profile.
- The machine is unclassified.
- The class fallback is withdrawn or blocked.
- A step rule points at a machine class whose machines differ (e.g. stone grinders at 10, 5 and 3 kg). It never averages.
- A rule's class has no operational machine with a capacity.
- A machine rated in litres meets a batch measured in kg. No density is assumed.
- The step evidence contradicts the governed route.
- The route lineage is missing.

**Switch.** `costing.plant_aware_load_switch` is installed empty, which means OFF.
- A row cannot start before 1 Nov 2026.
- Rows can only be closed, not edited, and every change is journalled.
- While OFF, and for every date before 1 Nov 2026, the wrapper `fn_au9_g4_route_step_loads` returns the current `fn_route_step_loads` value unchanged.

**Provenance.** `costing.route_step_load_provenance_snapshot` stores one row per step, per pool and per run. Each row records:
- the basis used, and the machine with how it is linked (route step or override)
- the equipment class
- the capacity profile id and its revision-journal id
- the step-rule id, the fallback-policy id and the legacy class row
- the charge, capacity and unit, the loads, the provisional flag, review flags and the switch id

Write guards on the provenance table:
- Rows are allowed only for an existing run of November 2026 or later.
- Rows cannot be changed or deleted.

The table is run-scoped, so new runs' fingerprints include it; runs 122 and 128 have no rows.

**Refresh RPC patch.** The patch is guarded:
- It runs only if each RPC's current text matches the reviewed md5. Expected live values: overhead 3087b71e…, labour 3b68b6aa…; both confirmed today.
- It swaps the 4 calls to `fn_route_step_loads(...)` for the wrapper, passing the step lineage.
- It writes provenance when the switch is ON.
- The overhead refresh raises an error if labour and overhead resolved the same step differently.
- It adds `plant_aware_load_switch_id` to the overhead refresh result.
